# Internationalization

Every visible string goes through i18n **from day one**, even when the app ships a single locale.

## Stack and layout

| Package | Role |
| --- | --- |
| `expo-localization` | Device locale (`getLocales()`) |
| `i18next` + `react-i18next` | Engine and React bindings |
| AsyncStorage (via the core storage client) | Persisted language preference, when the app offers one |

```plaintext
src/core/i18n/
  index.ts                     init (async) + `export default i18n`
  locales/
    pt-BR/translation.json
    en-US/translation.json     (when bilingual)
src/types/i18n.d.ts            CustomTypeOptions from the reference locale → typed keys
```

- `src/core/i18n/index.ts` initializes on import and is imported **once**, as a side effect, from `app/_layout.tsx` (`import "@/core/i18n";`). No `I18nextProvider` wrapper, no custom `useTranslation` wrapper.
- `compatibilityJSON: "v4"`, `interpolation.escapeValue: false`, an explicit `fallbackLng`.
- Locale resolution: saved preference (`"device"` or a tag) → device tag mapped to a supported locale (`pt*` → `pt-BR`) → fallback. The default locale is a product decision recorded in `AGENTS.md`.
- Native config: the `expo-localization` plugin with `supportedLocales` for iOS and Android.

## Keys

- Keys are English, nested by domain: `common.*`, `tabs.*`, `<feature>.*`, `screens.*`, `errors.*`, `validation.*`, `a11y.*` when labels are many.
- Plurals with i18next's `_one` / `_other` suffixes and `{ count }`, not hand-built conditionals.
- **Locale files stay symmetric.** A key in one locale and missing in another silently falls back and ships a mixed-language UI. A unit test compares the key sets of every locale file.
- Dead keys are removed with the UI that used them (dead-code sweep), in every locale at once.

## Usage

```tsx
// components, screens, hooks
import { useTranslation } from "react-i18next";

const { t } = useTranslation();
<Typography>{t("dashboard.title")}</Typography>;
<IconButton icon="settings" label={t("common.settings")} onPress={…} />;
```

```ts
// utils and code outside React — the singleton, no hooks
import i18n from "@/core/i18n";

i18n.t("tasks.completion", { percent: 75 });
```

- Never hardcode a user-facing string in JSX or in an `accessibilityLabel`.
- **Never translate user or API data** (names the user typed, catalog names).
- Format numbers, currency and dates with `Intl` in the active locale (`new Intl.NumberFormat(i18n.language, { style: "currency", currency })`) — never manual concatenation. Formatting helpers live in one module.
- A content language that differs from the UI language (e.g. the language of content fetched from an external catalog) is a separate preference with its own storage key, and changing it does not rewrite stored snapshots.

## Copy written outside the bundle

Store release notes and legal pages are the product speaking, so they follow the app's locales (declared in `AGENTS.md`). Their file names and surrounding docs stay English (chapter 00).
